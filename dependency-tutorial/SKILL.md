# dependency-tutorial

生成有可靠出处、可逐步实践的中文技术教程。读者具有 Java 和 Spring Boot 基础，但不了解目标组件。按“认识问题与核心概念 → 最小使用 → 常用能力 → 业务集成 → 源码与设计”的顺序教学；研究时先核实版本和资料，再据此编写示例。

## 1. 确定目标和版本

- 从请求中提取组件名称、学习目标、指定版本、运行环境和输出位置。组件名称有歧义且会影响资料选择时才澄清；不要因未提供版本而停下来询问。
- 用户明确指定版本时严格采用该版本。用户要求基于现有项目学习时，读取对应模块的构建文件、BOM、配置及实际解析依赖，把项目使用的版本作为约束；不要擅自升级项目。
- 其余情况实时查阅官网的下载、安装、Getting Started、支持策略或发布页面，默认采用官网推荐的版本。记录推荐依据、准确版本号、链接和查询日期，不能凭记忆认定“最新版”。
- 官网未明确推荐版本时，采用官方发布且适合目标环境的最新稳定版本，并说明这是稳定版回退选择；不要称其为“官网推荐”。除非用户要求，不采用 snapshot、alpha、beta、RC 或 nightly。
- 分开记录组件、客户端/服务端、集成模块或 starter、JDK、Spring Boot 以及必要外部服务的版本。查官方兼容性说明，不能假设这些版本号必须相同，也不能假设最新组件兼容当前 Spring Boot。
- 建立简洁的版本基线，至少包含：依赖坐标与版本、环境要求、文档版本、官方仓库、tag/commit。后续所有配置、API、源码分析和示例都对照此基线。兼容性冲突无法合理解决时，说明已核实的冲突并请求必要选择，同时继续独立研究。

## 2. 查阅官方文档、API 和配置

使用可用工具实际获取资料，不能只依据搜索摘要、工具的概括或模型记忆写教程。

- Context7 可用时，先解析准确的 library ID，再查询目标版本的文档。仅使用解析结果或用户提供的合法 ID，不猜测版本 ID。分别查询与教程相关的安装、核心 API、配置和关键行为，遵守工具调用限制。
- 检查 Context7 返回内容的版本与原始出处。如果只覆盖其他版本或未标明版本，改查官方版本文档、Javadoc/API Reference、发布说明及源码，不能把新版本示例直接改成旧版本号。
- 直接阅读官方 Quick Start、参考文档、配置说明、兼容性与迁移指南中相关部分。核对依赖坐标、包名、完整方法签名、配置前缀、默认值、启用条件与弃用信息。
- 官网默认展示的新版本页面未必适用于目标版本。优先版本化 URL；只有大版本或当前版文档时，用目标 tag 下的文档、发布说明、真实方法定义或发布包补充核验。
- Context7 无匹配、不可用或资料不足时，继续使用官方资料。不要为了完成教程而要求用户必须安装某个研究工具，也不要声称调用过不可用的工具。
- 发给外部检索工具的查询只包含公开组件名称、版本和研究问题；不发送项目密钥、个人信息或未获授权的私有代码。

## 3. 结合 DeepWiki 和真实源码研究原理

对开源组件，从官网或发布元数据确认官方 GitHub 仓库及对应模块。核实真实存在的版本标签和对应 commit，不假设标签一定是 `v版本号`，不以默认分支替代发布版本。

DeepWiki 可用且收录项目时，用它了解模块关系、入口和候选调用链。检查其索引版本；把总结当作导航线索，再到目标 tag/commit 的真实源码核对。DeepWiki 不可用或未收录时，直接阅读源码、官方架构文档及测试。非开源或无法访问源码时，明确原理讲解能验证到的边界，不能编造内部实现。

围绕示例中的一次具体操作追踪，不泛读整个仓库：

1. 找到用户调用的 API 或框架入口，核实所属包、类/接口、完整签名和运行时实现。
2. 找到对象的创建或注册位置、关键配置的读取/绑定位置以及触发条件。涉及 Spring 时，区分依赖引入、自动配置发现、条件判断、Bean 注册和实际方法调用。
3. 顺着真实调用逐个说明关键方法：谁调用谁，传入值来自哪里，返回值或状态被谁使用，接口与实现分别承担什么职责。
4. 追踪到可解释的结果，例如返回对象、HTTP 响应、SQL、缓存变化、消息发送/消费或文件输出。跨进程边界要分别查客户端和服务端；不能把客户端调用链当成完整服务端执行链。
5. 对会影响示例行为的代理、回调、异步调度、线程/上下文、异常和资源释放，说明执行顺序及边界。源码只能证明条件下的路径，不能证明运行时一定选用了某个分支。
6. 将重要节点关联到目标版本的源码路径与方法定义，优先使用 commit 固定的 GitHub 文件链接和核实后的行号。找不到 tag 时，核对发布包附带的 sources/Javadoc 与发布元数据，说明版本对应关系的证据和缺口。

解释关键设计时，连接“要解决的约束 → 采用的机制 → 带来的收益和代价 → 使用者受到的影响”。作者明确说明的设计理由引用官方材料；根据代码推导的理由标注为“设计推断”，不要把推断写成作者原话。

## 4. 设计循序渐进的实践示例

围绕一个适合组件的业务场景逐步增加能力，让后一阶段复用前一阶段的对象、配置和知识。不要每章换一套无关联的例子。

- **最小可运行案例：** 只引入完成核心操作所需的内容。给出项目/文件结构、必要且完整的构建配置、包名与 import、启动入口、配置、启动命令、调用方式和预期输出。可独立使用的组件优先简单 Java 案例；依赖 Spring 的组件采用最小 Spring Boot 应用。
- **常用 API：** 按实际任务扩展最小案例，讲清该 API 在场景中的作用、选择依据、参数与返回值。按使用过程组织章节，不按方法名称堆成清单。
- **业务集成：** 展示与 Java/Spring Boot 应用的真实衔接，例如配置绑定、Bean、Service 或 Controller，以及适用时的持久化、消息或缓存边界。只加入支撑场景的内容；对业务正确性有影响的重试、幂等、事务或并发行为要讲清。
- **常见错误及排查：** 挑选与这些示例和目标版本相关的错误，给出“可见现象/错误信息 → 原因或待证假设 → 检查位置/命令 → 修复 → 如何确认恢复”的链条。不要把未经验证的猜测写成已确定原因。

代码应可复制重建。完整最小案例中不要省略关键实现或用 `...` 代替必需内容；后续片段注明文件路径、替换/新增位置及其依赖的前文配置。区分框架自带类型与示例自定义类型，说明其来源和职责。

依赖版本显式固定，或由已固定版本的 parent/BOM 管理并说明实际解析版本；不要随意覆盖受管理的依赖。涉及外部服务时，提供兼容版本、必要启动/验证步骤、连接地址和停止方式，说明数据是否保留。示例使用可识别的本地测试配置和环境变量，不包含真实凭据。

## 5. 把重要 API 讲透

将 API 解释放在使用场景和代码旁边，必要时用小表格辅助比较。对影响读者理解或业务正确性的 API，按实际签名讲清：

- **定义与来源：** 所属类/接口、完整签名、关键泛型/重载，以及在哪个依赖中获得。
- **参数：** 每个重要参数表示什么、值来自哪里、类型与取值范围、单位、是否允许空值、默认值及参数之间的约束。不要凭参数名称猜测含义。
- **返回值：** 类型、具体内容与示例值、空值条件，以及结果代表哪个阶段。`void`、布尔值、Future、句柄或确认结果不能笼统解释为“操作成功”。
- **行为：** 同步/异步、是否阻塞、重要副作用、异常/失败方式，以及相关的超时、重试和资源生命周期。
- **场景与边界：** 何时使用、何时选其他 API、必要前置条件、线程安全/顺序/重复调用保证及版本限制；仅在与当前 API 相关且有证据时讨论这些性质。
- **设计原因：** 为什么采用该参数、返回类型、接口或调用方式，以及这种选择如何影响调用者。明确区别公共契约与当前版本的内部实现细节。

配置项也按“作用、类型/单位、默认值、所在文件/前缀、生效阶段、相关条件”解释。Java 方法参数、配置属性、HTTP 参数和表达式变量是不同来源，不要混为一谈。

## 6. 写成适合初学者的技术博客

- 先用具体问题说明组件是什么、解决什么问题、适用场景与必要核心概念，再引入安装和使用；让读者完成一次操作后再深入源码与设计。
- 用自然、连贯的中文解释。术语首次出现时给出中文含义与必要英文原名；不重复展开读者已经具备的 Java/Spring 基础。
- 代码前说明要做什么、为什么这样做；代码后解释关键语句、输入输出及如何判断结果。不要逐行复述显然的语法，也不要丢下一大段代码让读者自行理解。
- 对重要抽象概念同时提供类比和组件中的具体例子，明确类比中各角色对应什么及类比的局限；类比不能替代真实执行过程。
- 用 Mermaid 流程图或时序图解释关键抽象概念对应的执行流程、模块关系或异步交互，并解释关键节点。图中的类/方法、分支及顺序应与文字和证据一致；简化的概念图注明它省略了什么。不为简单语法或单个配置项机械配图。
- 每个深入章节回答一个使用过程中自然产生的问题。用已经运行或已解释的案例引出原理，而不是突然罗列架构术语、设计模式或无关技术。
- 根据目标组件的重要性和学习目标决定篇幅。不得为凑篇幅堆砌概念，也不能省略运行所需配置、关键 API 语义和影响正确性的技术细节。

## 7. 验证版本、示例和技术结论

对版本敏感的依赖、包名、方法重载、配置键、默认值、自动装配入口和弃用行为，逐项核对目标版本的官方资料或真实定义。历史版本差异可以单独解释，但不能混入主教程的可运行示例。

环境允许时，在隔离的示例目录完成适当的依赖解析、编译和最小运行，观察能证明教程主流程的结果。Java/Maven 示例可用 `dependency:tree` 或 effective POM 确认实际版本；验证公共 API 与关键配置，不为所有说明机械增加测试。使用本地测试资源，遵守当前工作区权限，不因写教程而修改既有业务或生产数据。

保持证据层级清楚：

| 依据 | 可以支持的表述 | 不能由此宣称 |
| --- | --- | --- |
| 官方文档/API 定义 | 目标版本规定的契约、配置及语义 | 示例已在本机成功运行 |
| 目标版本源码 | 给定条件下的实现与静态调用链 | 运行时一定进入该分支 |
| 编译/依赖解析 | API 类型可用、依赖可解析或代码可编译 | 外部服务或完整业务链路正常 |
| 实际运行证据 | 本次环境与输入下观察到的输出/行为 | 未测试条件下的通用保证 |

无法运行时，说明缺少的 JDK、构建工具、网络、服务或权限，给出复现命令并把输出标为“预期输出，尚未实测”。无法核实的重要内容在对应段落标为“未验证”；可合理推导的内容标为“基于源码的推断”。缺失证据不得用看似准确的数值、方法名、源码行号或伪造日志填补。

重要技术结论就近添加官方文档、Javadoc、固定版本源码或方法定义的 Markdown 链接。来源确实支持该结论，不能只链接仓库首页或仅在文末堆参考资料。Context7/DeepWiki 的内部结果标识不作为读者可用的引用；优先引用核对过的原始资料。资料互相矛盾时说明适用版本与证据边界。

## 8. 交付中文 Markdown 教程

按用户指定的位置和格式交付；未指定时采用当前工作区的交付约定，将完整教程保存为 `<component>-<version>-tutorial.md`。不只返回提纲或研究计划。示例项目文件仅在有助于复制运行或用户要求时一并交付。

根据实际内容调整章节，通常包含：

1. 标题、学习目标、版本基线与验证状态。
2. 组件解决的问题、适用场景和必要核心概念。
3. 环境准备、最小案例、执行步骤与结果解读。
4. 结合场景的常用 API 与渐进示例。
5. 业务集成及影响正确性的使用边界。
6. 从案例到关键类、接口、方法调用链与设计原因，配必要类比和 Mermaid。
7. 常见错误与排查、重要版本差异、参考资料及剩余验证限制。

交付前通读，确认版本基线一致、代码与配置能够按步骤重建、关键 API 语义有解释、抽象概念有具体对应、调用链有源码依据、引用能够定位相关定义、实际结果与预期输出分开标明。最后向用户说明教程位置、覆盖内容、实际完成的验证以及影响使用的未验证项。
